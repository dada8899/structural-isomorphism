# Production `.env` override policy

**Status**: Active
**Last updated**: 2026-05-21 (session #16)
**Related**: `SESSION-15-INCIDENT-deploy-pipeline.md` #3 / `feedback_env_override_pre_pr_check.md`

---

## Why this exists

Session #15 incident: the in-code default for `ASK_LLM_MODEL` was changed,
the change went through PR review, CI green, deploy succeeded — and yet
prod still used the OLD model. Root cause: a stale `ASK_LLM_MODEL=…` line
in `/root/Projects/structural-isomorphism/web/backend/.env` on the VPS
silently overrode the code default. Reviewers never thought to check the
prod env file because no PR ever touched it.

The rule: **prod `.env` should hold secrets and host-specific knobs ONLY.
Anything that has a meaningful default in code does NOT belong in `.env`
unless we're consciously overriding it.**

---

## What MUST be in prod `.env`

These have no sensible code default; they belong in `.env`:

| Variable | Why |
|---|---|
| `DEEPSEEK_API_KEY` | Secret |
| `OPENROUTER_API_KEY` | Secret |
| `STRUCTURAL_SHARE_TOKEN_SECRET` | Secret (M1.4 share token HMAC) |
| `OPENAI_API_KEY` (if used) | Secret |

## What MUST NOT be in prod `.env` unless we're actively A/B testing

These have meaningful code defaults — keeping them in `.env` causes drift:

| Variable | Code default | Why excluded |
|---|---|---|
| `ASK_LLM_MODEL` | `deepseek/deepseek-chat:nitro` | Session #15 was 5 days of stale-deploy because this was set in prod `.env`. |
| `ASK_RELEVANCE_TOP1_MIN` | `0.75` | Threshold lives in code, tuned via PR not env. |
| `ASK_RELEVANCE_TOP3_MEAN_MIN` | `0.65` | Same. |
| `LLM_MODEL` (used by `llm_service.py`) | `anthropic/claude-sonnet-4.6` | Same. |
| `LLM_TRANSLATE_MODEL` | `anthropic/claude-haiku-4.5` | Same. |

If a feature flag style override is genuinely needed, put it in
`web/backend/feature_flags.yaml` or pass it via the request, NOT prod
`.env`.

## What is generated by deploy (don't hand-edit)

These are written by `scripts/deploy-vps.sh` on every deploy into
`web/backend/.env.runtime`:

| Variable | Source |
|---|---|
| `STRUCTURAL_GIT_SHA` | `git rev-parse --short=12 HEAD` at deploy time |
| `STRUCTURAL_BUILD_DATE` | Deploy timestamp |
| `STRUCTURAL_DEPLOYED_AT` | Deploy timestamp |
| `STRUCTURAL_ENV` | Fixed `"prod"` |

`main.py` loads `.env.runtime` AFTER `.env` with `override=True` so the
runtime fingerprint always wins.

## Audit procedure (run before any prompt / model PR)

```bash
# 1. Run the fingerprint check — confirms what model prod will actually call.
python3 scripts/dogfood_fingerprint.py

# 2. SSH the VPS and grep .env for anything in the "MUST NOT" list above.
ssh root@43.156.233.71 'grep -E "^(ASK_LLM_MODEL|ASK_RELEVANCE|LLM_MODEL|LLM_TRANSLATE_MODEL)=" /root/Projects/structural-isomorphism/web/backend/.env || echo "[OK] no banned overrides found"'
```

If step 2 returns any matches, decide:
- **Intentional A/B**: Document why in the PR body; add a TODO with the planned removal date.
- **Stale**: Delete the line, run `systemctl restart structural-web`, re-run fingerprint check.

## Automation — what's wired now (session #16)

- `/api/version` returns `model` so any client (dogfood / CI / monitoring)
  can detect a mismatch.
- `scripts/dogfood_fingerprint.py` exits non-zero on model / git_sha
  mismatch — wire it into nightly cron if you want passive monitoring.
- `scripts/deploy-vps.sh` writes `.env.runtime` with `STRUCTURAL_GIT_SHA`
  so prod always reports what code it's on.
