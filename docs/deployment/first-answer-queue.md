# Private first-answer queue and schema bridge

The local background queue is one immutable job per saved question revision. It is not a provider, an execution grant, or a second copy of the question. It stores the owner, revision/digest/version, permission epochs, bounded state and timestamps, a transient random running fence, and a result reference. The only optional prose is one validated clarification of at most 240 characters; a verbatim copy of the question is rejected. The user session is used to authorize the enqueue/read/cancel request and is never stored in the queue.

The worker takes one job only after acquiring the exclusive lock on `research-first-answer-queue.lock` beside the canonical private Auth database. Preprovision this empty regular file under the Main service UID with mode 0600 and one link. Preserve its inode across running releases; do not replace, truncate, or unlink it to force a second worker. Startup and schema migration do not create it. Main startup without an available local worker may leave the runner disabled.

A worker restart obtains the lock first, then retires any durable `running` job as `failed/interrupted`. It never repeats that inference; a job still `queued` was not sent and can be considered for dispatch. Cancellation, stale revision, and account erasure invalidate the fence. Completion writes the result and the terminal status in a single transaction. A failed database commit may be retried with the already obtained result, never by resending the inference. Terminal state is idempotent; a new saved revision is required for a new execution.

## Migration and rollback

- Existing schema 15 remains supported and the queue is closed. Provision the final schema 16 with `scripts/bootstrap-private-runtime.py --offline-migrate-first-answers` only after the approved persistent backup and exclusive stop procedure. The receipt includes `first_answer_queue_protocol: 1`. Table, indexes, guards, and version marker commit atomically.
- The final schema 16 catalog includes the queue. An older experimental schema 16 without the queue is not a valid source for an in-place repair. No experimental schema 16 was intended for production; discard isolated fixtures or restore their original v15 backup, then apply the final migration.
- Roll back product behavior with a release that accepts **this exact** v16 catalog and leaves the queue runner disabled. Keep private job reads, cancellation, and account deletion available. Do not start an earlier v16 or v15 binary on this database. A binary rollback to v15 requires the independently verified v15 backup/restore route and reconciliation of intervening writes; never drop the queue or change the marker in place.
