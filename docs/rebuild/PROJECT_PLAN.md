## 立项与交付边界

**这是既有系统改造，目标是交付清晰、可靠的跨领域研究产品，而非重建空仓或重写全部代码。** 用户已确认三项能力及持续执行方向，明确要求按 Project OS 完整立项和交付。需求与授权依据见 [需求权威页](https://chatgpt.com/space/page_1cfcb3669b7881919ef320608251e8c6) 和 [规划独审记录](reviews/PLANNING_REVIEW.md)；公开阅读入口见 [改造索引](README.md)，实际执行状态由本地 PMO 入口维护。

| 用户任务 | 首版须交付的完整结果 | 不可混淆的证据 |
| --- | --- | --- |
| 现象解题 | 澄清现象和目标，给跨领域候选、数学模型、已有方法出处、迁移条件及最小验证 | 描述相似、模型适用、来源领域方法有效、迁移有效分别判断 |
| 公式对应 | 公式与变量、单位、变换、假设和边界可查，区分严格等价、近似、局部结构相似和不成立 | 字符替换或 LLM 判断不等于数学验证 |
| 深度研究 | 通过实际产品链路检索并核对原文，必要时执行分析，输出观点与证据对应、冲突、限制及下一实验 | 内部 KB、预置样例和生成建议不等于完成外部研究或原创发现 |

首版允许有限模型家族与有出处案例，但不能把三项能力削减为普通类比聊天。具体覆盖和验收由 Product Manager 在委派内细化；若关键证据推翻方向，提交 Mentor 处理受影响范围，其他工作继续。

现阶段不扩张到任意领域自动证明、投资预测承诺、自动原创发现或新的收费商业化。Phase、旧工具、公开 API、研究包和论文资产按接管与功能去留矩阵处理，不能未检查使用和依赖便关闭或删除。

## 非生产集成线与首次 CI 接线

PMO 已只读核对当前完整基线的 workflow 和 GitHub main 保护；Architecture 窄审同意采用受控集成线。该方案尚未执行，须在正式 B1 准入后由单一协调者建立分支，不复制未冻结的共享 WIP。

`main` 保持生产代码权威，本轮集成分支保存经审改造候选，不替代已发布版本。规划、候选修复、CI Bootstrap 和共享契约依当前检查合入集成线；共享契约冻结后，模块从同一完整 SHA 并行。最终 release PR 才进入 main，并重新满足最终候选独审、当前必要 CI、完整 QA 和发布门禁，不把集成线绿色等同上线。

| 现场事实 | 规划处理 |
| --- | --- |
| `ci.yml`、`sanity.yml`、`types-sync.yml`、`beta-perf.yml`、`coverage.yml` 的 push／PR 分支当前只覆盖 main | CI Bootstrap 仅增加精确集成线及 Bootstrap 候选所需触发，保留真实执行与 coverage，不扩大为所有分支或无意义全触发 |
| CI `release-gate` 聚合八个真实依赖，manifest 要求跨 workflow 的四个检查 | 保留八依赖及 `release-gate`、`sanity`、`check`、`beta-perf-audit`；接入新契约探针，不能减少、跳过或软化必要结果 |
| main 保护实际要求上述四检查且 strict=true；现有 rulesets 列表为空 | 这是只读时点事实；新集成线不自动继承。首次受控合并前核是否被规则覆盖，必要时由有管理权限者按精确方案新增该线保护并回读，不修改或削弱 main，不借管理员绕过 |
| Beta／Phase／Docs 的 push 发布监听 main；部署还支持未见 ref 限制的手动 dispatch，包发布有 tag／dispatch 入口 | 不能只凭 push 条件声称完全隔离。集成期间不发生产 dispatch 或发布 tag；Bootstrap 审查核 ref 限制和否定路径，任何真实发布继续受独立门禁约束 |
| `ci.yml` 的非必要 live e2e 对任意 push 执行且 soft-fail | 增加集成 push 前明确将其保留为生产／发布观察信号，避免离线集成检查访问旧生产；八个必要依赖仍完整执行，真实公网验收不因此豁免 |

首次接线采用一项独立 CI Bootstrap 候选：从固定受审基线建立暂不接产品变更的集成分支；候选为自身精确分支增加 push 触发、为集成 base 增加 PR 触发，让候选内真实 workflow 实际执行。核独审、检查范围、发布隔离和 required check 可识别后，才合并 Bootstrap→集成线 PR；回读新集成 merge SHA 并取得该版本检查成功，再接候选修复与 B1 共享实现。若触发未发生或状态未知，停在接线待验并修正原因，不空过、不删除门禁，也不先合 main 来解套。

每项证据记录 event、workflow revision、run／attempt、PR head、base 和实际 checkout SHA。PR 合并测试提交与 head 不混称，集成 merge SHA 另核对应检查。手动 dispatch 结果不作为 PR 必要检查的替代。分支保护变更由 PMO 列精确范围、Mentor 核边界，有权限者执行并回读；当前未创建集成分支、未改 workflow 或保护，也未发任何 dispatch。

每个公共文件、配置和锁文件只有一个 owner。开发任务卡绑定 task／attempt、Issue、绝对工作树、branch、base SHA、contract revision、允许／禁止路径、前置解除人、验收与停止／恢复条件。开发者提交自己的 PR，不自合并；公共契约变化先改 owner 冻结新 revision，再迁移消费者。

仓库为 PUBLIC，PMO 在提交前核明确路径及实际正文，只发布公开安全的产品、架构、审查和计划。DevOps 的真实连接信息、账号标识、余额数值及用户数据不得进公开 commit／Issue；仅在私有、权限 600、不含 secret 的元数据证据留回执，公开材料呈现核实结论与脱敏定位。Session 身份、故障现场、本地绝对路径及 source-map 按最小必要管理，不把所有未跟踪材料自动全提交，也不使用 `git add -A`。

开发准入与真实执行条件分开登记。工具凭据、余额或生产恢复未闭合时，已获准入的离线模块和安全边界可以继续；对应真实调用／迁移／发布保持待验，不能以离线结果解除。B1 的共享冻结先验证可观察状态及合法后态，产品显示“完成”不得掩盖执行未结束、证据不足、在途费用或访问已撤销。

## 验收与整体结束

验收分成软件机制、真实执行、数学／研究正确性、用户使用四层。每份证据注明需求版本、完整代码／制品身份、环境、输入、方法、结果、日期与未验条件。模型自述、字段名 `validated`、HTTP 200 或进程 active 均不能替代任务结果。

**技术验收通过**要求三个真实任务闭环及必要失败／权限／预算／恢复通过，最终 SHA 的独审和必要 CI 有真实结果，目标 VPS 的制品与数据、公开访问和恢复得到验证。**待用户实际使用**必须给可操作入口、代表任务和遗留限制。**整体完成**还要求用户实际使用结果、清理清晰度、维护责任和必要备份期限均有记录；不能发布后立即自行结项。

上线观察的时间、次数、指标、停止信号和负责人在 R1 之前依据服务风险明确登记；未登记或未达到不声称稳定运行。不得以无限观察代替结束条件，也不能以人为评分抵消核心任务失败。

## 回收与恢复执行

PMO 活动回合内持续回收：派发→有界等待／读回→核当前结果与版本→独审→原作者返修→新 SHA 复核→更新状态→下一已授权动作。`wait_threads` 不可用时有界 `read_thread` 对账；没有实测回合外调度，不承诺回合结束后自动接续。

阻塞登记具体依赖、解除证据、解除人及下一安全动作；原范围失败修复继续，只有真实越界、无法判断的关键影响或外部条件才集中升级。外部动作回执未知先查实际目标，不能盲重试。恢复前核旧作者实际停写与资源。Mentor 已回读旧四会话均停止、全部在途工具结束并归档可恢复；完整接管结束前仍不清理旧树。旧材料和独有资产仅作历史输入，由新 owner 复核，不能直接迁入替代新任务。

本计划未执行提交、push、合并、部署或清理；PMO 三文件交 Mentor 做 Astra 规划独审后，按新基线继续。
